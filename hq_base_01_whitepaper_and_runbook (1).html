1. Executive Summary & Design Philosophy

The HQ-BASE-01 trust fabric governs high-integrity state transitions across cryptographic attestation envelopes, Write-Once-Read-Many (WORM) audit checkpoints, monotonic EMV chip counters, and authority key lifecycle events. Rather than relying on best-effort retries or permissive defaults when backing stores experience contention or partial unavailability, HQ-BASE-01 enforces fail-closed semantics backed by SERIALIZABLE PostgreSQL transactions and domain-separated Ed25519 signatures.

This combined artifact provides both an architectural whitepaper and a multi-subsystem operational runbook. Part I establishes the threat model, core invariants, and end-to-end verification flow executed by pg-combined-e2e-live.test.ts and orchestrated by run-live-test.mjs. Part II details step-by-step operational procedures, failure modes, diagnostic queries, and recovery playbooks for every subsystem.

Core Architectural Invariants
  • Monotonicity & Max-Wins Reconciliation: Counter state never regresses; reconciliation elevates persistent or atomic state to the maximum observed counter without rolling back higher values.
  • Fail-Closed Unreadiness: Guards refuse acceptance until readiness checks, atomic runners, and transactional stores are verified healthy.
  • Domain-Separated Cryptographic Authority: Rollovers, attestations, superseding records, and revocations bind explicit domain tags and canonical preimages prior to Ed25519 verification.
  • Durable Supersession & Nonce Guarding: Corrective attestations persist durably in PostgreSQL and enforce single-use nonce/expiry semantics to block replay attacks.

2. System Architecture & Subsystem Topology

HQ-BASE-01 separates protocol schema and signature verification from stateful persistence and atomic replay enforcement while binding them together inside ingestHqBase01Envelope and resolveCheckpointAttestation.

Module / Component Responsibility Failure Posture
hq-base-01-schema-gate.ts Canonical hashing (sha256CanonicalHex), domain preimage construction (buildDomainPreimage), envelope types, and in-memory superseding ledger. Rejects malformed schemas, mismatched domain tags, or invalid signatures.
pg-retry-transactional-client.ts Wraps pg.Pool transactions with configurable isolation (SERIALIZABLE), statement timeouts, jittered backoff, and SQLSTATE 40001 retry handling. Retries transient serialization conflicts up to budget; surfaces exhausted errors cleanly.
durable-ledger-and-replay.ts Persists superseding attestations in hq_superseding_attestations and hydrates ledger snapshots for checkpoint resolution. Fails transactionally if durable write or hydration query fails.
hybrid-fail-closed.ts Evaluates atomic replay and time-bounded nonce scripts (evalNonceScript) to detect duplicate or expired nonces. Rejects replays (REPLAY_DETECTED) or expired nonces; fails closed on runner faults.
emv-counter-warmup.ts, emv-counter-reconcile.ts, emv-dual-write-counter.ts Initializes guard readiness, reconciles SQL (hq_replay_counters) and atomic counters using max-wins semantics, and advances monotonic EMV counters. Blocks counter advancement when unready or when incoming counter is not strictly greater than current state.
hq-base-01-integration.ts Coordinates envelope ingestion, key rollovers, WORM checkpoint chain verification (verifyWormCheckpointChain), key revocations, and attestation status resolution. Rejects untrusted/revoked keys (KEY_REVOKED), broken hash links, or unverified digests.

3. Combined Live PostgreSQL E2E Test (pg-combined-e2e-live.test.ts)

The combined end-to-end test exercises the full lifecycle against a live PostgreSQL instance (skipping gracefully when PostgreSQL is unreachable) and cleans up synthetic rows in a finally block.

  1. Bootstrap & Schema Setup: Connects via DATABASE_URL (defaulting to postgres://postgres:postgres@127.0.0.1:5432/hq_base_01_test), ensures hq_replay_counters and hq_superseding_attestations exist, instantiates RetryingPgTransactionalClient in SERIALIZABLE mode, and seeds an initial SQL counter of 30 alongside an atomic counter of 34.
  2. Max-Wins Reconciliation & Counter Advance: Runs reconcileEmvCountersMaxWins so the state elevates to 34 without regressing, marks the guard ready, and executes advanceAndPersistEmvCounter to advance to 35.
  3. Key Rollover & WORM Chain Verification: Signs a hq-base-01.key-rollover.v1 record with the root authority key, ingests it via ingestHqBase01Envelope, constructs a two-node WORM checkpoint chain linked by SHA-256 digests, verifies it with verifyWormCheckpointChain, and confirms initial ORIGINAL resolution.
  4. Durable Superseding & Nonce Replay Guard: Signs and ingests a hq-base-01.superseding-attestation.v1 envelope with a bounded nonce window (ACCEPTED_AND_PERSISTED), replays the identical nonce parameters to verify rejection (REPLAY_DETECTED), hydrates from PostgreSQL via DurableSupersedingStore.loadLedgerSnapshot, and verifies SUPERSEDED status.
  5. Key Revocation & Post-Revocation Fail-Closed Check: Signs and ingests a hq-base-01.key-revocation.v1 record targeting the delegated attestor key, then re-submits attestation1 to verify it is rejected with KEY_REVOKED.

function makeKeypair() {
  const { publicKey, privateKey } = generateKeyPairSync("ed25519");
  const spki = publicKey.export({ format: "der", type: "spki" }) as Buffer;
  return {
    publicKeyHex: spki.subarray(spki.length - 32).toString("hex"),
    privateKey,
  };
}

function signPreimage(
  privateKey: ReturnType<typeof createPrivateKey>,
  tag: string,
  payload: JsonValue
): string {
  return cryptoSign(null, buildDomainPreimage(tag, payload), privateKey).toString("hex");
}

    const atomicCounters = new Map<string, number>([[seqKey, 34]]);
    const seenNonces = new Map<string, number>();

    const atomicRunner: AtomicCounterSeedRunner & AtomicScriptRunner = {
      async getCounter(key) {
        return atomicCounters.get(key) ?? null;
      },
      async seedOrRaiseCounter(key, counter) {
        const cur = atomicCounters.get(key);
        if (cur === undefined || counter > cur) {
          atomicCounters.set(key, counter);
          return true;
        }
        return false;
      },
      async evalCounterScript(key, incomingCounter) {
        const cur = atomicCounters.get(key) ?? 0;
        if (incomingCounter <= cur) return 2;
        atomicCounters.set(key, incomingCounter);
        return 1;
      },
      async evalNonceScript(key, nowMs, expiresAtMs) {
        if (nowMs > expiresAtMs) return 3;
        const exp = seenNonces.get(key);
        if (exp !== undefined && exp >= nowMs) return 2;
        seenNonces.set(key, expiresAtMs);
        return 1;
      },
    };

    const store: KeyStateStore = {

5. Subsystem 1: Transactional Client & Serialization Retry

Operational Scope

RetryingPgTransactionalClient executes transactional callbacks under PostgreSQL SERIALIZABLE isolation with bounded statement timeouts and retries serialization failures (SQLSTATE 40001) using exponential backoff and jitter.

Runbook Procedures

  • Health & Connection Check: Verify SELECT 1 latency and active connection pool utilization before starting high-concurrency ingestion.
  • Serialization Contention Tuning: Adjust maxRetries, baseDelayMs, maxDelayMs, and jitterRatio when hot-key contention spikes.
  • Diagnostic Query: Inspect long-running or blocked transactions in PostgreSQL: 
    SELECT pid, state, wait_event_type, wait_event, now() - query_start AS age, query
FROM pg_stat_activity
WHERE datname = current_database() AND state <> 'idle'
ORDER BY age DESC;

6. Subsystem 2: Fail-Closed EMV Monotonic Counter & Reconciliation

Operational Scope

FailClosedEmvCounterGuard, reconcileEmvCountersMaxWins, and advanceAndPersistEmvCounter maintain strictly monotonic EMV chip sequence counters across hq_replay_counters and the atomic counter store.

Runbook Procedures

  • Reconciliation on Startup or Drift: Execute reconcileEmvCountersMaxWins so lower counters (e.g., SQL 30) are raised to the higher atomic value (e.g., 34) without rolling back higher counters.
  • Counter Advancement: Call advanceAndPersistEmvCounter only when emvGuard.isReady() is true and incomingCounter exceeds the current accepted counter.
  • Inspect Counter Rows: 
    SELECT seq_key, instrument_id, highest_accepted_counter, updated_at_ms
FROM hq_replay_counters
ORDER BY updated_at_ms DESC
LIMIT 50;

7. Subsystem 3: Hybrid Atomic Replay & Nonce Guard

Operational Scope

HybridAtomicReplayGuard evaluates atomic nonce scripts (evalNonceScript) using channel, domainId, subjectId, nonceOrId, contextHash, nowMs, and expiresAtMs.

Runbook Procedures

  • Duplicate / Replay Investigation: When ingestion returns REPLAY_DETECTED, verify whether the client retried with the same nonceOrId and contextHash within the active TTL window.
  • Clock & Expiry Verification: Confirm nowMs <= expiresAtMs across application nodes so valid nonces are not prematurely expired due to clock skew.

8. Subsystem 4: WORM Checkpoint Chain & Attestation Resolution

Operational Scope

verifyWormCheckpointChain validates sequential checkpoint links, SHA-256 payload/checkpoint digests, and signer credentials across WORM checkpoint nodes, while resolveCheckpointAttestation determines whether an attestation is ORIGINAL or SUPERSEDED.

Runbook Procedures

  • Chain Integrity Audit: Verify that node N+1 sets prev_checkpoint_digest_sha256 equal to node N's checkpoint_digest_sha256 and that raw payload bytes hash to the declared digest.
  • Status Resolution Check: Hydrate ledger state via DurableSupersedingStore.loadLedgerSnapshot before evaluating resolveCheckpointAttestation after restarts or failover.

9. Subsystem 5: Key Rollover, Superseding Ledger & Revocation

Operational Scope

ingestHqBase01Envelope processes hq-base-01.key-rollover.v1, hq-base-01.superseding-attestation.v1, and hq-base-01.key-revocation.v1 envelopes.

Runbook Procedures

  • Key Rollover Execution: Sign the rollover preimage with an authorized root key, verify domain_scope and epoch bounds (epoch_start, epoch_end, grace_epochs), and confirm accepted: true.
  • Superseding Attestation Audit: Verify durable persistence in hq_superseding_attestations: 
    SELECT attestation_id, target_checkpoint_id, target_attestation_id, issued_at_ms, recorded_at_ms
FROM hq_superseding_attestations
ORDER BY recorded_at_ms DESC
LIMIT 50;
  • Emergency Key Revocation: Issue a hq-base-01.key-revocation.v1 envelope signed by a security_officer or root_authority key; confirm subsequent attestations from the revoked key fail with KEY_REVOKED.
